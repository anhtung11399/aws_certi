Phản ứng sự cố: điều tra, cô lập, khôi phục

Thu thập bằng chứng, tương quan log, đánh giá phạm vi, cô lập và loại bỏ mối đe doạ (EC2, credential, S3, container, Lambda), khôi phục, root cause analysis với Detective.

Học xong bài này bạn sẽ:
  • Biết đúng thứ tự xử lý từng loại sự cố
  • Giữ bằng chứng đúng cách
  • Tìm nguyên nhân gốc

#Thu thập bằng chứng (forensic artifacts)

Bằng chứngCách thuLưu ý
Bộ nhớ (RAM)Công cụ (LiME, AVML, WinPmem) chạy qua SSM Run Command, ghi ra S3Thu trước khi tắt máy, dễ mất nhất
ĐĩaSnapshot EBS mọi volume (có thể copy sang account forensics, mã hoá bằng key của forensics)Không gắn volume gốc vào máy khác khi chưa có bản sao
Metadata instanceDescribeInstances, tag, SG, IAM role, ENI, user dataGhi lại trước khi đổi gì
LogCloudTrail, Flow Logs, DNS logs, log OS / ứng dụng, ELB / WAF logsXuất ra bucket bằng chứng có Object Lock, ghi hash để chứng minh không bị sửa
ContainerSnapshot node, docker export / checkpoint, log của pod, EKS audit
LambdaLấy bản code và cấu hình của version đang chạy (GetFunction), log CloudWatch

Giữ chain of custody: ai thu, lúc nào, hash SHA-256, lưu ở đâu, ai truy cập. Bucket bằng chứng: versioning + Object Lock compliance + SSE-KMS + bucket policy chỉ cho role forensics.

#Tìm kiếm, tương quan và đánh giá phạm vi

  • Xác thực finding: là thật hay báo động giả (máy quét nội bộ, pentest đã báo trước)? Dùng Detective xem bối cảnh, CloudTrail xem API cụ thể.
  • Đánh giá phạm vi: principal bị ảnh hưởng đã làm gì (CloudTrail Lake / Athena theo access key ID hoặc session), đã tạo thêm tài nguyên / credential nào, đã truy cập dữ liệu nào (S3 data events), lan sang account nào (AssumeRole cross-account), Region nào.
  • Tương quan: IP của kẻ tấn công trong Flow Logs, WAF logs, CloudTrail sourceIPAddress; user agent; khung thời gian.
  • Security Lake + Athena (OCSF) hoặc OpenSearch Security Analytics khi cần tương quan nhiều nguồn.

#EC2 bị chiếm quyền: thứ tự xử lý

Đây là dạng câu ordering rất hay gặp. Nguyên tắc: giữ bằng chứng, cô lập, không tắt máy vội (tắt máy là mất dữ liệu trong RAM).

  1. Bật termination protection, gắn tag đánh dấu (ví dụ Quarantine=true), ghi lại metadata của instance.
  2. Tách khỏi ASG (detach hoặc đặt standby) và deregister khỏi target group, để ASG không terminate mất bằng chứng và người dùng không còn bị phục vụ bởi máy này.
  3. Cô lập mạng: đổi sang security group cách ly không có rule nào (hoặc chỉ cho máy điều tra). Lưu ý: kết nối đang mở (tracked connection) có thể vẫn còn với SG; dùng NACL để cắt ngay nếu cần.
  4. Thu bằng chứng: snapshot các EBS volume, chụp bộ nhớ (memory dump bằng công cụ qua SSM), lưu log.
  5. Điều tra trong account forensics: tạo volume từ snapshot, gắn vào máy điều tra (đã cô lập).
  6. Loại bỏ và khôi phục: thay bằng instance mới từ AMI sạch, vá lỗ hổng, xoay vòng credential liên quan.

Đáp án "terminate instance ngay" hoặc "stop instance để chụp snapshot" thường là bẫy: mất bằng chứng trong RAM, và tắt máy trước khi điều tra không cần thiết. Tuy nhiên nếu đề ưu tiên "ngăn thiệt hại ngay lập tức" hơn điều tra thì cô lập mạng luôn là bước đầu.

#Credential bị lộ

IAM user access key lộ (ví dụ đẩy lên GitHub)

  1. Vô hiệu hoá (deactivate) access key ngay. AWS có thể đã tự gắn policy AWSCompromisedKeyQuarantine và gửi thông báo qua Health.
  2. Tra CloudTrail mọi hành động của key đó: tạo user mới, key mới, role, instance... rồi dọn hết.
  3. Xoay vòng: tạo key mới cho ứng dụng (tốt hơn: chuyển sang role), xoá key cũ.
  4. Kiểm tra hoá đơn và mọi Region (máy đào coin).

Credential tạm thời của role bị lộ

  • Không "xoá" được credential tạm thời đã cấp. Dùng Revoke active sessions trên role: IAM gắn policy Deny mọi request có aws:TokenIssueTime trước thời điểm thu hồi.
  • Bật IMDSv2 để giảm nguy cơ SSRF lấy credential.

Root bị lộ

  • Đổi mật khẩu, bật / thay MFA, xoá access key của root (root không nên có access key), kiểm tra CloudTrail, liên hệ AWS Support.

#Điều tra nguyên nhân gốc

  • Detective: từ một finding, xem IP / role / instance liên quan, hành vi trước và sau, so với bình thường.
  • CloudTrail Lake / Athena truy vấn ai làm gì, từ IP nào, user agent nào.
  • Kiểm tra lỗ hổng được khai thác bằng Inspector, đối chiếu WAF / ALB log.
  • Root cause analysis xong: sửa nguyên nhân (vá, siết policy), thêm control phòng ngừa (SCP, Config rule), cập nhật runbook.

Câu hỏi nhanh. Sắp xếp đúng thứ tự khi phát hiện EC2 trong ASG bị chiếm: (1) snapshot EBS, (2) detach instance khỏi ASG, (3) đổi sang security group cách ly. Thứ tự nào hợp lý nhất?

Detach trước để ASG không thay thế mất máy, cô lập mạng để chặn thiệt hại, rồi thu bằng chứng.

Câu hỏi nhanh. Credential tạm thời của một role trên EC2 bị đánh cắp và đang được dùng từ IP bên ngoài. Cách vô hiệu hoá nhanh nhất mà không xoá role?

Credential tạm thời không xoá được. Revoke active sessions chặn mọi token cấp trước thời điểm đó.
