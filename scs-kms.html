KMS, CloudHSM, key material và Private CA

Key type, key policy, grant, envelope encryption, encryption context, rotation, multi-Region key, imported key material, external key store, CloudHSM, Private CA, xử lý lỗi KMS.

Học xong bài này bạn sẽ:
  • Đọc hiểu key policy
  • Phân biệt AWS generated và imported key material
  • Chọn KMS, CloudHSM hay XKS

#Các loại key

LoạiAi quản lýGhi nhớ
AWS owned keyAWS, dùng chung nhiều khách hàngKhông thấy, không kiểm soát, miễn phí
AWS managed key (aws/s3, aws/ebs...)AWS tạo trong account bạnKhông sửa key policy, không chia sẻ cross-account được, tự xoay vòng hằng năm
Customer managed keyBạnTự viết key policy, grant, bật / tắt, xoay vòng (tự động 90 đến 2560 ngày, hoặc on-demand), chia sẻ cross-account, xoá sau 7 đến 30 ngày chờ
  • Symmetric (AES-256, mặc định, dùng cho gần như mọi dịch vụ) và asymmetric (RSA / ECC để ký hoặc mã hoá ngoài AWS, tải được public key), HMAC.
  • Multi-Region key: cùng key material ở nhiều Region (primary + replica), giải mã ở Region khác không cần gọi về Region gốc. Dùng cho DynamoDB Global Tables, DR, mã hoá phía client.
  • Imported key material (BYOK): bạn tự tạo key material và nhập vào. Bạn chịu trách nhiệm độ bền, có thể đặt thời hạn hết hạn, xoá ngay lập tức. Không tự xoay vòng được.
  • Custom key store: key nằm trong CloudHSM của bạn, hoặc external key store (XKS) ở ngoài AWS.

#Envelope encryption

Dịch vụ như S3, EBS, RDS làm việc này tự động. Tự mã hoá phía client: dùng AWS Encryption SDK.

#Key policy: phần quan trọng nhất

  • Mỗi KMS key bắt buộc có key policy. Không như các tài nguyên khác, IAM policy chỉ có tác dụng khi key policy có câu cho phép account root:
Câu mặc định: uỷ quyền cho IAM của account quyết định
{
  "Sid": "Enable IAM policies",
  "Effect": "Allow",
  "Principal": { "AWS": "arn:aws:iam::111122223333:root" },
  "Action": "kms:*",
  "Resource": "*"
}
  • Thiếu câu này thì dù IAM policy cho phép, user vẫn không dùng được key. Xoá nhầm và không ai còn quyền → phải liên hệ AWS Support.
  • Tách vai trò: key administrator (quản lý key, không mã hoá / giải mã được) và key user (dùng key, không sửa policy).
  • Cross-account: key policy cho phép account kia và IAM policy ở account kia cho phép user của họ.
  • Điều kiện hay dùng: kms:ViaService (chỉ dùng key thông qua một dịch vụ, ví dụ s3.ap-southeast-1.amazonaws.com), kms:CallerAccount, kms:EncryptionContext:*.
  • Grant: cấp quyền dùng key tạm thời, có thể thu hồi, hay được dịch vụ AWS dùng (EBS, RDS tạo grant khi gắn volume).
  • Encryption context: cặp key-value đi kèm khi mã hoá, phải khớp khi giải mã. Ghi vào CloudTrail, dùng để kiểm toán và làm điều kiện trong policy.

  • Quy trình import: tạo key với origin EXTERNAL → GetParametersForImport (wrapping public key RSA + import token, hết hạn sau 24 giờ) → bọc material → ImportKeyMaterial.
  • Rotation của KMS giữ nguyên key ID / ARN, giữ material cũ để giải mã dữ liệu cũ; dữ liệu cũ không bị mã hoá lại. Rotation bằng tay kiểu cũ: tạo key mới và đổi alias sang key mới.
  • Multi-Region key: rotation áp cho cả primary và replica; imported material phải import cùng material vào từng replica.

#External key store (XKS)

  • Key nằm trong hệ thống quản lý khoá bên ngoài AWS (HSM on-premises / nhà cung cấp khác). KMS gọi tới XKS proxy của bạn cho mỗi thao tác mã hoá / giải mã.
  • Bạn kiểm soát tuyệt đối: ngắt proxy là AWS không giải mã được gì ("hold your own key").
  • Đánh đổi: độ trễ cao hơn, phụ thuộc tính sẵn sàng của hệ thống bên ngoài, bạn chịu trách nhiệm độ bền.
  • Kết nối proxy qua Internet hoặc VPC endpoint service.

#Grant, encryption context và dịch vụ tích hợp

  • Grant: uỷ quyền tạm thời, có grant constraint (encryption context), thu hồi bằng RevokeGrant / RetireGrant. Dịch vụ AWS (EBS, RDS, Redshift) tạo grant thay bạn; người dùng cần kms:CreateGrant với điều kiện kms:GrantIsForAWSResource.
  • Encryption context: cặp key-value không bí mật đi kèm mã hoá, phải khớp khi giải mã (additional authenticated data). S3 dùng ARN bucket / object, EBS dùng volume ID. Dùng trong điều kiện kms:EncryptionContext:... để giới hạn key chỉ giải mã cho đúng tài nguyên.
  • kms:ViaService: chỉ cho dùng key thông qua dịch vụ cụ thể. kms:CallerAccount, kms:GrantIsForAWSResource.
  • AWS Encryption SDK: mã hoá phía client với envelope encryption, data key caching, nhiều key (multi-keyring) để giải mã ở nhiều Region.

#Private CA và chứng chỉ nhiều Region

  • AWS Private CA: dựng CA phân cấp (root CA tự ký, subordinate CA), cấp chứng chỉ private cho dịch vụ nội bộ, mTLS, thiết bị IoT, VPN, Roles Anywhere. Private CA là tài nguyên Regional; cấp chứng chỉ cho nhiều Region bằng cách tạo subordinate CA ở từng Region, hoặc dùng ACM ở Region khác với CA được chia sẻ (RAM).
  • Chế độ short-lived certificate (tối đa 7 ngày, rẻ hơn) cho workload tự xoay vòng.
  • Thu hồi: CRL (lưu S3) hoặc OCSP.
  • Key của CA nằm trong HSM do AWS quản lý (FIPS 140-3). Bảo vệ CA root: tách account, quyền chặt, CloudTrail theo dõi IssueCertificate.
  • ACM là Regional: cần chứng chỉ ở nhiều Region (ALB đa Region) thì yêu cầu / import ở từng Region; CloudFront luôn ở us-east-1.

#Xử lý sự cố KMS

LỗiNguyên nhân
AccessDeniedException khi giải mãKey policy / IAM thiếu kms:Decrypt, hoặc điều kiện ViaService / encryption context không khớp
DisabledException / KMSInvalidStateExceptionKey bị disable hoặc đang chờ xoá. Huỷ lịch xoá (cancel deletion) trong thời gian chờ để cứu
ThrottlingExceptionVượt quota request KMS. Dùng S3 Bucket Key, cache data key (Encryption SDK), xin tăng quota

Sợ xoá nhầm key: tạo CloudWatch alarm / EventBridge rule trên CloudTrail event ScheduleKeyDeletion, và dùng SCP cấm kms:ScheduleKeyDeletion trừ role quản trị. Thử trước bằng cách disable key thay vì xoá.

#CloudHSM

  • HSM chuyên dụng một khách hàng (single-tenant), chuẩn FIPS 140-3 level 3, bạn toàn quyền quản lý key, AWS không truy cập được key.
  • Dùng khi: cần kiểm soát độc quyền, giao thức chuẩn (PKCS#11, JCE, CNG), SSL/TLS offload cho web server, Oracle TDE, ký code, CA riêng.
  • Bạn tự lo high availability: cluster ít nhất 2 HSM ở 2 AZ.
  • KMS cũng đạt FIPS 140-3 level 3 hiện nay; chọn CloudHSM khi đề nhấn mạnh "single-tenant", "customer exclusive control", "PKCS#11".

Câu hỏi nhanh. IAM policy của user cho phép kms:Decrypt trên một customer managed key nhưng user vẫn bị AccessDenied. Key policy chỉ có một câu cho phép role Admin. Vì sao?

Với KMS, key policy là điểm quyết định. Chỉ khi key policy uỷ quyền cho account thì IAM policy mới được xét.

Câu hỏi nhanh. Yêu cầu: key mã hoá phải nằm trong HSM single-tenant do công ty kiểm soát độc quyền, nhưng vẫn muốn S3 / EBS tích hợp KMS bình thường. Giải pháp?

Custom key store giữ key trong CloudHSM của bạn mà dịch vụ AWS vẫn dùng qua API KMS.
