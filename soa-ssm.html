Systems Manager toàn tập

Managed node, Run Command, Automation runbook, Patch Manager, State Manager, Maintenance Windows, Session Manager, Parameter Store, Inventory, OpsCenter, Incident Manager, Distributor, Change Manager, hybrid activation.

Video bài giảng sẽ được cập nhật sau
Học xong bài này bạn sẽ:
  • Chọn đúng tính năng SSM cho từng việc
  • Vá lỗi máy chủ hàng loạt an toàn
  • Viết và chạy runbook tự khắc phục

#Systems Manager là gì

AWS Systems Manager (SSM) là bộ công cụ để quản lý máy chủ và vận hành ở quy mô lớn: chạy lệnh, vá lỗi, giữ cấu hình, vào shell, lưu cấu hình, tự động hoá quy trình. Đây là dịch vụ được hỏi nhiều nhất trong SOA sau CloudWatch.

#Managed node: điều kiện bắt buộc

Điều kiệnChi tiết
SSM AgentCó sẵn trên Amazon Linux 2 / 2023, Ubuntu, Windows Server AMI của AWS. AMI khác phải tự cài
Quyền IAMInstance profile có AmazonSSMManagedInstanceCore. Hoặc bật Default Host Management Configuration (DHMC): SSM tự cấp quyền cho mọi EC2 trong account / Region mà không cần gắn role
MạngGọi ra HTTPS 443 tới ssm, ssmmessages, ec2messages: qua Internet / NAT, hoặc VPC interface endpoint cho 3 dịch vụ đó (thêm s3 gateway endpoint để tải patch / log, kms nếu mã hoá phiên, logs nếu ghi log)
Máy on-premises / cloud khácHybrid activation: tạo activation code + ID, cài agent, đăng ký. Máy có ID dạng mi-xxxxxxxx. Tier Advanced cần cho Session Manager trên máy hybrid với nhiều máy

Máy không hiện trong Fleet Manager: kiểm tra đúng 3 điều trên theo thứ tự agent → quyền → mạng. Đáp án "mở cổng 22" hay "gắn Elastic IP" luôn sai: SSM không cần cổng vào nào.

#Document: "kịch bản" của SSM

  • Viết bằng JSON / YAML. Loại: Command (Run Command, State Manager), Automation (runbook), Session, Package (Distributor), Policy.
  • Có sẵn hàng trăm document của AWS (tên bắt đầu AWS-, AWSSupport-, AWSConfigRemediation-, AmazonCloudWatch-). Tự viết document riêng và chia sẻ cho account khác hoặc công khai.
  • Document hay gặp: AWS-RunShellScript, AWS-RunPowerShellScript, AWS-RunPatchBaseline, AWS-ConfigureAWSPackage, AWS-UpdateSSMAgent, AWS-ApplyAnsiblePlaybooks, AWS-RestartEC2Instance, AWS-StopEC2Instance, AWS-CreateImage, AWS-UpdateLinuxAmi, AWSSupport-ResetAccess, AWSSupport-TroubleshootSSH, AWS-DisableIncomingSSHOnPort22, AWSConfigRemediation-EnableS3BucketEncryption.

#Run Command

  • Chạy một document Command trên nhiều máy ngay bây giờ, không cần SSH / RDP.
  • Chọn máy: theo tag, theo resource group, chọn tay, hoặc tất cả.
  • Rate control: concurrency (số máy / % chạy cùng lúc) và error threshold (dừng khi số máy lỗi vượt ngưỡng).
  • Output: xem trên console (giới hạn 2.500 ký tự), đầy đủ thì ghi về S3 hoặc CloudWatch Logs.
  • Thông báo khi xong / lỗi qua SNS, hoặc event trong EventBridge.
  • Toàn bộ lệnh được ghi lại trong CloudTrail: ai chạy gì trên máy nào.

#Automation (runbook)

  • Quy trình nhiều bước, chạy ở phía AWS (không cần agent cho các bước gọi API). Mỗi bước là một action: aws:executeAwsApi, aws:runCommand, aws:executeScript (Python / PowerShell), aws:invokeLambdaFunction, aws:createImage, aws:waitForAwsResourceProperty, aws:branch, aws:approve (chờ người duyệt), aws:sleep...
  • Chạy bằng role (AutomationAssumeRole), không dùng quyền của người bấm: người vận hành chỉ cần quyền chạy runbook, không cần quyền trực tiếp lên tài nguyên.
  • Cách kích hoạt: tay, theo lịch (State Manager / Maintenance Window), EventBridge, CloudWatch alarm, Config remediation, Change Manager.
  • Chạy trên nhiều tài nguyên (rate control theo tag) và nhiều account / Region từ một account trung tâm (cần role AWS-SystemsManager-AutomationExecutionRole ở account đích).
  • Ví dụ thực tế: AWS-UpdateLinuxAmi tạo AMI đã vá; runbook "khi đĩa đầy thì mở rộng EBS"; runbook của AWS Support chẩn đoán lỗi kết nối.
Runbook rút gọn: snapshot volume rồi gắn tag
schemaVersion: '0.3'
assumeRole: '{{ AutomationAssumeRole }}'
parameters:
  VolumeId: { type: String }
  AutomationAssumeRole: { type: String }
mainSteps:
  - name: createSnapshot
    action: aws:executeAwsApi
    inputs: { Service: ec2, Api: CreateSnapshot, VolumeId: '{{ VolumeId }}' }
    outputs:
      - { Name: SnapshotId, Selector: $.SnapshotId, Type: String }
  - name: waitDone
    action: aws:waitForAwsResourceProperty
    inputs:
      Service: ec2
      Api: DescribeSnapshots
      SnapshotIds: ['{{ createSnapshot.SnapshotId }}']
      PropertySelector: $.Snapshots[0].State
      DesiredValues: [completed]

#Patch Manager

Khái niệmGiải thích
Patch baselineQuy tắc vá: hệ điều hành nào, phân loại (Security, Bugfix...), mức độ (Critical, Important), auto-approve sau N ngày, danh sách patch được duyệt / bị chặn tường minh, có vá cả ứng dụng không (Windows). Mỗi OS có baseline mặc định của AWS, có thể tạo baseline riêng và đặt làm mặc định
Patch groupGắn máy với baseline bằng tag key Patch Group (hoặc PatchGroup). Một máy chỉ thuộc một patch group, một patch group chỉ gắn một baseline cho mỗi OS
OperationScan (chỉ kiểm tra, báo cáo thiếu bản vá) hoặc Install (cài và có thể reboot). Tuỳ chọn RebootOption: RebootIfNeeded / NoReboot
Patch policy (Quick Setup)Cách mới: một chính sách vá cho nhiều account / Region trong Organization, lịch scan và install riêng
ComplianceBáo cáo máy nào thiếu bản vá gì, xuất ra S3 / xem ở Explorer, Security Hub

Quy trình chuẩn: Maintenance Window (lịch, ví dụ Chủ nhật 2 giờ sáng, dài 3 giờ, dừng nhận việc mới trước khi hết 1 giờ) → target là patch group → task chạy AWS-RunPatchBaseline với Install → rate control 20% máy mỗi lần → output về S3.

Muốn vá trên môi trường dev trước rồi mới tới prod với đúng tập bản vá đã thử: dùng baseline có approval theo số ngày giống nhau và chạy dev sớm hơn, hoặc chụp danh sách patch đã duyệt (approved patches) để prod dùng đúng danh sách đó.

#State Manager

  • Association: "máy khớp điều kiện X phải luôn được áp document Y theo lịch Z". Máy mới khớp tag sẽ tự được áp.
  • Ví dụ: luôn cài CloudWatch agent, luôn cập nhật SSM Agent, luôn chạy Ansible playbook, luôn bật firewall Windows, thu Inventory mỗi 30 phút.
  • Khác Run Command: Run Command là chạy một lần, State Manager là duy trì liên tục (chống drift cấu hình).

#Maintenance Windows

  • Định nghĩa khung giờ được phép làm việc gây gián đoạn: schedule (cron / rate), duration, cutoff (dừng bắt đầu task mới trước khi hết giờ), time zone.
  • Target: máy theo tag, resource group. Task: Run Command, Automation, Lambda, Step Functions, có priority và rate control.
  • Dùng cho: vá lỗi, chụp AMI, chạy script bảo trì, khởi động lại dịch vụ.

#Session Manager

  • Vào shell (Linux) / PowerShell (Windows) qua console hoặc CLI (aws ssm start-session), không mở cổng vào, không bastion, không key SSH.
  • Kiểm soát bằng IAM: ai được mở phiên tới máy nào (theo tag), được chạy document phiên nào.
  • Ghi log toàn bộ phiên về S3 và / hoặc CloudWatch Logs, mã hoá phiên bằng KMS. CloudTrail ghi StartSession.
  • Port forwarding: chuyển tiếp cổng tới máy, hoặc tới host khác qua máy đó (ví dụ vào RDS trong private subnet từ laptop). Dùng được với ssh / scp qua ProxyCommand.
  • Chạy với user ssm-user mặc định, cấu hình Run As để chạy bằng user OS khác (theo tag của IAM principal).
  • Giới hạn thời gian phiên rảnh (idle timeout), tối đa thời gian phiên.

#Parameter Store

StandardAdvanced
Số parameter10.000100.000
Kích thước4 KB8 KB
Parameter policies (Expiration, ExpirationNotification, NoChangeNotification)KhôngCó
Chia sẻ cross-account (RAM)KhôngCó
PhíMiễn phí lưuTính phí
  • Kiểu: String, StringList, SecureString (mã hoá KMS, dùng key mặc định aws/ssm hoặc customer managed key).
  • Cấu trúc phân cấp: /myapp/prod/db/url. Lấy cả nhánh bằng GetParametersByPath. Phân quyền IAM theo đường dẫn.
  • Có lịch sử phiên bản, nhãn (label), có event trong EventBridge khi đổi.
  • Public parameters của AWS: ID AMI mới nhất (/aws/service/ami-amazon-linux-latest/...), danh sách Region, dịch vụ. Dùng trong CloudFormation để luôn lấy AMI mới.
  • Đọc secret của Secrets Manager qua Parameter Store: /aws/reference/secretsmanager/<tên>.
  • Throughput mặc định thấp, bật higher throughput (tính phí) nếu ứng dụng đọc nhiều; tốt hơn là cache trong ứng dụng.

Câu hỏi nhanh. Đội muốn vá OS cho 500 máy ở 12 account, mỗi tuần, có báo cáo tập trung, ít công sức nhất. Giải pháp?

Patch policy của Quick Setup áp lịch vá cho nhiều account / Region từ một nơi, có báo cáo compliance tập trung.

Câu hỏi nhanh. Người vận hành cần chạy runbook khởi động lại EC2 production nhưng không được có quyền ec2:RebootInstances trực tiếp. Cách thiết kế?

Automation chạy bằng role riêng, tách quyền của người kích hoạt khỏi quyền thực hiện.

Câu hỏi nhanh. Developer cần kết nối từ laptop tới RDS trong private subnet để gỡ lỗi, không có VPN, không bastion mở cổng. Cách làm?

Session Manager hỗ trợ port forwarding tới host từ xa (AWS-StartPortForwardingSessionToRemoteHost) mà không mở cổng vào.

Câu hỏi nhanh. Máy chủ on-premises cần được quản lý bằng Run Command và Patch Manager như EC2. Bước cần làm?
